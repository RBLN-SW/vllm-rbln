# Async scheduling on RBLN — state of the work, 2026-08-13

Async decoding is **8.97% faster per step** than sync and produces **identical
output text**, on the same invocation and the same build. It needs a
`rebel_compiler` change to be worth anything: without it async ties sync.

One known gap: **structured output is broken under async scheduling** (§6).

## 1. Which branches this needs

The feature spans two repos and the pair is not optional.

| repo | branch | carries |
| --- | --- | --- |
| vllm-rbln | `async-scheduling` | the scheduler, the async output path, the token feedback |
| rebel_compiler | `dwkang-fixups` (`aed721d78c`) | the device-resident sampler patch plus the vmemory copy fix |

`dwkang-fixups` = `dwkang/sampler-token-device-resident` + two commits of mine
(`63dde65dfd` fix, `aed721d78c` format). The vmemory half is also open on its
own as `yskim/vmem-padded-wt-dst-copy` (`4cff70d22d`).

A build with only one half does not merely run slower: plain `origin/dev`
rebel_compiler does not start against this branch at all, because vllm-rbln
consumes the sampler's dense `(B,)` output and the older converter yields a
different shape.

## 3. Decode performance

Per-step wall clock, median over 20 probe windows per arm, max_tokens 1024:

| | step (ms) | sample (ms) |
| --- | --- | --- |
| **async** | **17.032** | 0.479 |
| sync | 18.709 | 0.456 |

**async is 8.97% faster per step.**

The vmemory fix is what makes that gap exist. With the fast path refused — the
`origin/dev` behaviour — the sampler's staging copy costs **12.35 ms per step**
and async lands at **18.501 ms**, i.e. level with sync. The fix takes the
staging copy to 0.48 ms and the whole gap appears there.

End-to-end tok/s is not the metric to judge this by: round-to-round spread on
this workload is ~3% even with `ignore_eos`, larger than several effects worth
chasing, and async only touches decode. Use the per-step probe.

| arm | Pearsonr | verdict |
| --- | --- | --- |
| async | 0.995679 | PASS |
| sync | 0.995679 | PASS |

Threshold is 0.99. The two arms agree to the last digit, so async contributes
nothing of its own to the gap against native.

**Output health.** Adjacent-equal token ids across all 32 completions:
**29 / 32736** (0.09%). This exists because a wrong-but-symmetric build can pass
the arm-to-arm check — see §7.

## 5. What the vmemory fix is

The sampler's graph output has user shape `[8]` int32 and physical shape `[64]`:
`contrib_top_k_top_p_sample` writes each token splatted across a 64-lane group
(`tensor<8x64xi32>`), `reshape_last_dim` compacts that on device to
`tensor<64xi32>` with the 8 tokens adjacent at the head, and a
`contrib_aligned_pad` with `pad_width = [0, -56]` presents `[8]` to torch
without moving bytes. That last op is what the runtime records as the tensor's
`op_replay`, and it is applied lazily by whoever copies the tensor.

vllm-rbln stages that output into a ring buffer (`rbln_sampler.py`), which is a
device-to-device copy of a padded `WITH_TRANSFORM` destination. `PlanPvToPvCopy`
refused every such destination, and the fallback drains pending transfers and
copies synchronously — the 12.35 ms.

The fix: when src and dst agree on the layout byte for byte and the whole tensor
is being copied, move **each allocation's physical extent verbatim, padding
included**. The extent is read off the transform itself (the span from the first
to the last element its replay places in that allocation), so a sharded tensor
gets one copy per shard at its own `alloc_idx`.

The padding is not optional. Skipping it — writing only the mapped elements —
makes the model emit each token twice: 22664 of 32736 adjacent token ids equal,
and the text shortens from 132065 to 111125 characters, with no error raised.

Untouched by the fix, deliberately:

- destinations without padding, where the element mapping already moves every
  byte that means anything (this preserves the shard walk and the mapping-count
  ceiling the unit tests pin),
- dtype-converting copies, excluded by the physical-meta equality check,
- `EMPTY_INIT_WITH_ZERO` destinations, whose padding owes zeros that src's
  padding does not promise — the #11047 guard still fires for them.

The 128B alignment rule in `d2d_multi_copy_cmd_buffer.cc` is not involved. It
decides only whether a copy is batched into a command stream; both batched and
individually-encoded copies land in the same command buffer and the same
dispatch.

## 6. Known gap: structured output

`tests/torch_compile/e2e/test_structured_output.py` fails 6 of 10 on this
branch and passes on vllm-rbln `origin/dev`.

Isolated by holding everything else fixed: forcing
`scheduler_config.async_scheduling = False` makes it pass; bypassing the sampler
ring buffer does not; reverting `copy_plan.cc` to `origin/dev` does not, and
fails byte-identically. The run log shows `AsyncScheduler` only on the branch.

Structured output advances its grammar from the tokens the scheduler can see,
and the async path leaves a `-1` placeholder there until the writeback lands, so
the mask is built from a token that was never sampled. Generation is then
unconstrained — a JSON-schema request returns unparseable text, with no error.

This is reachable without anyone asking for async: vLLM resolves an unset
`--async-scheduling` to enabled, and its exclusion list
(`vllm/config/vllm.py`) covers pooling and some speculative decoding but not
structured output. It reaches the OpenAI `response_format` path and tool
calling.

Two routes, not yet taken: make the async output path give the grammar the real
sampled tokens, or exclude structured-output requests from schedule-ahead. The
latter has to be decided per request — `structured_outputs_config` always
exists, so a config-level test cannot detect it.

## 7. How to measure this without fooling yourself

Both of these cost real time on 2026-08-12.

**Arm-to-arm text equality is not a correctness gate.** A build that corrupts
output corrupts both arms identically, and `cmp_texts.py` still reports 32/32.
Compare against a known-good build — character totals and the adjacent-equal
token count are enough to catch it — or run the native golden.

**Check which binary you actually ran.** Every run log prints
`Resolved version: 0.11.2.dev<N>+g<hash>`, and that hash is the commit the `.so`
was *built* from, not the branch checked out. A rebase without a rebuild
produced a set of numbers belonging to an orphaned commit, and the branch that
was actually pushed had the opposite behaviour.
