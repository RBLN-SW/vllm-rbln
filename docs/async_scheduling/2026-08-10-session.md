# Async scheduling: correctness restored, and where the step time goes

State on 2026-08-10, after the `dev` merge into vllm-rbln and rebel_compiler.
Model gpt-oss-120b, b=8, DP4+EP, mt=1024, greedy, 32 prompts, via
`docs/async_scheduling/ab_throughput.sh` on the vllm-rbln-executor venv.

## 1. Measurement, before anything else

Three defects made every earlier number meaningless. All are fixed and
committed; a run that predates them cannot be compared against.

- The harness left `VLLM_RBLN_SAMPLER` unset, so the executor defaulted it to 0
  and the runs measured the **CPU sampler** (692709ac). `Using RBLN sampler.`
  on all four workers is the check.
- `HF_HUB_OFFLINE` / `TRANSFORMERS_OFFLINE` killed the runs outright; both were
  removed (692709ac).
- Async did not run at all after the merge: `RBLNAsyncScheduler.schedule()` had
  drifted from its base signature (cd082a95).

Two rules that came out of this:

- **Judge correctness only on `input text -> output text` equality.** Async does
  not emit logprobs, so logits, Pearson r and `--run-iter` all say nothing.
  `docs/async_scheduling/cmp_texts.py` joins arms on the prompt string, never on
  list position. Copy inputs to distinct basenames first - it keys its `arms`
  dict on the basename and two files named `async_r1.outputs.json` collapse.
- **Judge performance on the per-step probe, not tok/s.** tok/s swings ~3%
  between rounds of the same arm (BASE async 409.3 / 421.5, sync 423.4 / 406.6),
  which is larger than any effect measured here. `VLLM_RBLN_STEP_PROBE=200`
  reports per-region wall/cpu/p50/p90/p99 over 200 steps per rank, with <1%
  spread.

## 2. Correctness

Fixed in 04315eb8. Async and sync agree 32/32, and async reproduces itself
32/32 across processes.

The bug: `_bookkeeping_sync` writes `sampled_ids = [-1]` in the async path and
extends `CachedRequestState.output_token_ids` with it. `token_ids_cpu` is
rebuilt from that state when a request re-enters the batch, so repairing only
`token_ids_cpu` was not enough - and the old repair also dropped requests that
were out of the batch at writeback time. Both fire constantly here because RBLN
pins the prefill batch to 1, so unscheduled requests are evicted from the
persistent batch every step. `_apply_pending_token_writeback` now repairs the
request state as well, indexed off `num_prompt_tokens`.

## 3. Performance: the step is not host-bound

async 18.04 ms/step vs sync 18.53 - about **2%**, against the 7% seen before the
merge (19.0 vs 20.6). The merge did not slow async down; it made the host ~2.2 ms
cheaper, and only sync could bank all of that.

Removing host work does not shorten the step. Cutting 1.08 ms of host CPU moved
`blocked` up by the same amount and left the step 0.2 ms *longer*. Whatever the
remaining 2% costs, it is not host work sitting on the critical path.

## 4. The token feedback, and the 128-byte rule

`tok_feedback` cost **1.10 ms every step** (cpu 0.50). It is one statement:

```python
staged_model_inputs.input_ids[:n, 0] = prev_sampled[:n, 0]
```

Ruled out by measurement: pending device work (`torch.rbln.synchronize()`
returns in 7 us immediately before it), the copy path itself, the destination,
the position in the step, dtype, shape, stride on its own, and `non_blocking`.
A control copy with identical shape, dtype, stride and destination but a
host-written source costs 7 us.

The cause is an alignment rule. `prev_sampled` is a column of the sampler's
(B, 64) int32 ring, so this is a device-to-device copy of **eight 4-byte pieces
at 256B stride**, and the async D2D command buffer accepts only 128B-aligned
addresses *and* sizes:

```cpp
// rebel/src/runtime/vmemory/d2d_multi_copy_cmd_buffer.cc:22
constexpr uint64_t kAlignment = 128;
return (copy.src_addr() % kAlignment) == 0 && (copy.dst_addr() % kAlignment) == 0 &&
       (copy.size() % kAlignment) == 0;
```

Every piece is rejected - the runtime's reject axis reports 8 rejects per call -
and the fallback calls `DrainAsyncTransfers()`. That drain is the 1.10 ms.

**D2H and H2D carry no such rule.** `copy_cmd_buffer.cc` and
`multi_copy_cmd_buffer.cc` have no alignment check, and the same strided column
copies with zero rejects.

### The fix (uncommitted, measured)

Route the feedback through the host - D2H the strided column, H2D the dense
result into `input_ids`:

```python
host.copy_(prev_sampled[:n_fb, 0])                    # D2H, no reject
staged_model_inputs.input_ids[:n_fb, 0].copy_(host)   # H2D, no reject
```

|              | BASE   | host hop |
| ------------ | ------ | -------- |
| tok_feedback | 1.099  | 0.165    |
| sample       | 0.349  | 0.418    |
| attn.build   | 11.504 | 10.966   |
| **step**     | 18.040 | **17.321** |

**-0.72 ms/step (-4.0%), output text 32/32 identical to both sync and BASE
async.** vllm-rbln only; no compiler change.

## 5. Dead ends, so they are not rewalked

Four attempts to make the sampler graph return a dense (B, 1) instead of the raw
(B, 64). All are worse than BASE; the compiler tree is restored.

| attempt                                        | sample  | step  |
| ---------------------------------------------- | ------- | ----- |
| BASE (raw (B,64), staging ring)                 | 0.349   | 18.04 |
| torch-level `argmax(...)[:, :1].contiguous()`   | 12.378  | 18.35 |
| converter `contrib_reshape_last_dim(n_pad=63)`  | 12.579  | 19.12 |
| converter `contrib_take_last_dim(n_pad=63)`     | compile error: `invalid host op detected; must add a converter` |
| converter `contrib_pad_last_dim(n_pad=63)`      | 12.580  | 19.12 |

Facts worth keeping:

- **The depad does get deferred, exactly as designed.** With
  `contrib_pad_last_dim`, `RBLN_PRINT_JSON_GRAPH=1` shows
  `output_pv[0]: dev=rbln shape=[8,64] hostOpSeq=[{'pad': {'pad_width': [...,'63']}}]`
  and the only extra node is `__nop`, which `tvm_graph_processor.cc:40` maps to
  `TvmNodeBodyCase::NOP` and the converter skips. There is **no host op** and no
  `EnsureAllTasksCompleted` drain. An earlier reading of mine claimed otherwise;
  it was wrong.
- The cost lands in the **staging copy**, not the graph call: splitting the
  `sample` region gives `sample.graph` 0.41 ms and `sample.copy` 11.95 ms
  (cpu 0.30 - it is a wait). Copying out of a depadded tensor is again 8x4B and
  hits the same 128B rule.
- Ring allocation matters to which rejection you get. `torch.empty(shape,
  device=rbln)` inherits the source's padded layout via
  `CreateAllocConfigMatchingPv` and is rejected as `kWtDstPadding`;
  `torch.zeros(shape).to(device)` allocates flat and clears the reject - but then
  the async path is attempted and fails outright with
  `rbln_memcpy_v2v_async failed (4 bytes)`, which is the alignment rule again.
- **The ring is not load bearing for correctness.** Removing it keeps output text
  32/32. It is load bearing for performance: without it, `sample` goes 0.349 ->
  12.305 and the step to 19.90. Output buffer addresses move every call whether
  the previous output is held or not, and alternating two compiled sampler
  instances does not change that - so the ring cannot be replaced by address
  rotation.

## 6. Tools

- `mk_sampler.py` (scratchpad) compiles the sampler graph alone in ~30 s instead
  of loading a 120B model for 3 minutes. With `RBLN_PRINT_JSON_GRAPH=1` and
  `RBLN_DUMP_PATH=<dir>` it writes the graph JSON, which is the authority on
  partitioning: `output_pvs[*].hostOpSeq`, and node ops/func_names.
- The runtime exports the copy reject axis over ctypes -
  `rbln_prof_v2v_reject_num_reasons`, `rbln_prof_get_v2v_reject`,
  `rbln_prof_reset_v2v_reject` in `librbln.so`. Reason names are in
  `rebel/include/rebel/runtime/vmemory/copy_plan.h`. This is the fastest way to
  ask why a copy left the fast path, and needs no rebuild.
