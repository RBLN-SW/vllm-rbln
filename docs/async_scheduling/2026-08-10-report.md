# Async scheduling vs sync — end-to-end result, 2026-08-10

Async decoding is **7.8% faster per step** than sync and produces **identical
output text**. Both numbers are on the same invocation, same build, same day.
Rebased onto `origin/dev` the gap is **7.5%**, with the same 32/32 text match.

Working notes and the reasoning behind the change are in
[2026-08-10-session.md](2026-08-10-session.md).

## Setup

| | |
| --- | --- |
| model | openai/gpt-oss-120b, gpt_oss_mxfp4 |
| parallelism | DP=4 + EP, batch 8, prefill batch pinned to 1 |
| decode | greedy, max_tokens 1024, 32 prompts, ignore_eos |
| driver | `docs/async_scheduling/ab_throughput.sh`, 2 rounds per arm |
| probe | `VLLM_RBLN_STEP_PROBE=200` — 200 steps per report, per rank |

## Decode performance

Per-step wall clock, median over 4 ranks x 2 rounds x every 200-step window
(n=40 windows per arm):

| | step (ms) | host cpu | blocked |
| --- | --- | --- | --- |
| **async** | **17.120** | 4.925 | 12.393 |
| sync | 18.564 | 5.171 | 13.535 |

**async is 7.78% faster per step.**

Re-measured after squashing the branch and rebasing it onto `origin/dev`, which
brought in ten upstream commits including
`03faefb1 perf(compile): enable static output for decode model graphs`:

| | step (ms) | host cpu | blocked |
| --- | --- | --- | --- |
| **async** | **16.922** | 4.552 | 12.513 |
| sync | 18.291 | 4.675 | 13.674 |

**async is 7.49% faster per step**, and both arms picked up a little absolute
speed, which is the shape the upstream compile change predicts. Output text is
again identical across all six arm pairs, 32/32 prompts, and the async unit
tests pass (58).

Text cannot be compared across the two measurements: the gpt-oss chat template
embeds `Current date:` in the system prompt, and the runs fall on different
days, so the prompt strings themselves differ. Within either day, async and sync
answer identically, which is the property that matters.

### max_tokens 256

Same result at the other compiled length, two rounds per arm:

| | step (ms) |
| --- | --- |
| **async** | **17.207** |
| sync | 18.508 |

**+7.03%**, and async/sync output text matches 32/32.

End-to-end tok/s is not usable at this length and should not be quoted: the
prefill batch is pinned to 1, so 8 prompts per rank are prefilled serially
against only 256 decode steps, and the run is prefill-dominated. Rounds spread
6-13% and one arm produced no warm samples at all. Async only touches decode,
so it has to be judged per decode step.

### Decode-only throughput

The probe measures decode steps by construction, so decode throughput is just
the concurrency over the step time - 8 sequences per rank x DP 4 = 32 tokens per
step:

| | async | sync | |
| --- | --- | --- | --- |
| mt=1024 | 1891 tok/s | 1749 tok/s | +8.1% |
| mt=256 | 1860 tok/s | 1729 tok/s | +7.6% |

## The DP all_reduce overlap is real

The per-step DP num_tokens all_reduce is issued in `_prepare_inputs` and waited
on in `_determine_batch_padding`, so it can overlap the device.
`dp_reduce.wait` still reports 1.0-1.2 ms, which looks like the overlap is not
working. It is - that figure is what is left after overlapping. Turning the
split off (`VLLM_RBLN_DP_ALL_REDUCE_ASYNC=0`, one blocking call at the use site)
costs:

| | step (ms) | host cpu |
| --- | --- | --- |
| split on (default) | 16.922 | 4.552 |
| split off | 17.874 | 5.566 |

**0.95 ms/step, 5.6%.** Worth keeping, and the higher CPU with it off is the
blocking collective burning the main thread.

Where the step goes, per region (async r1):

| region | async | sync |
| --- | --- | --- |
| attn.build | 10.368 | 1.020 |
| sample | 0.729 | 0.586 |
| tok_feedback | 0.181 | — |
| dp_reduce.wait | 0.924 | 0.827 |

`attn.build` differs because the arms wait for the device in different places,
not because either does more work; the totals above are what matters.

End-to-end tok/s, for reference only — round-to-round spread on this workload is
~3%, larger than most effects, so the per-step probe is the primary metric:

| round | async | sync |
| --- | --- | --- |
| r1 | 445.6 | 418.5 |
| r2 | 426.1 | 411.5 |

async's worst round still beats sync's best.

## Correctness

Judged the only way that is meaningful here — same prompt in, same text out.
Async emits no logprobs, so logits, Pearson r and `--run-iter` say nothing.
`cmp_texts.py` joins arms on the prompt string.

| pair | identical |
| --- | --- |
| async r1 vs async r2 | 32/32 |
| async r1 vs sync r1 | 32/32 |
| async r1 vs sync r2 | 32/32 |
| async r2 vs sync r1 | 32/32 |
| async r2 vs sync r2 | 32/32 |
| sync r1 vs sync r2 | 32/32 |

All six pairs match on all 32 prompts. Async is also reproducible across
processes, which it was not before this session.

## What moved

| | step (ms) | async vs sync |
| --- | --- | --- |
| session start (post-merge) | async 18.04 / sync 18.53 | +2.1% |
| **now** | **async 17.12 / sync 18.56** | **+7.8%** |

sync is unchanged (18.53 -> 18.56). The gain is entirely async getting faster,
which is the right shape: it means the work was removed, not shifted onto the
baseline.

Two changes account for it.

1. **Correctness** (04315eb8). The async path writes a `-1` placeholder into
   `CachedRequestState.output_token_ids`, and `token_ids_cpu` is rebuilt from
   that state whenever a request re-enters the batch — which happens every step
   here, because RBLN pins the prefill batch to 1 and evicts unscheduled
   requests. `_apply_pending_token_writeback` now repairs the request state too.
   Before this, 28 of 32 prompts diverged from sync.

2. **Token feedback through the host** (this session, section 4 of the notes).
   `input_ids[:n, 0] = prev_sampled[:n, 0]` is a device-to-device copy of eight
   4-byte pieces at 256B stride, and the async D2D command buffer requires 128B
   alignment on address *and* size
   (`d2d_multi_copy_cmd_buffer.cc:22`). Every piece was rejected and the
   fallback drained pending transfers: **1.10 ms of every step**. D2H and H2D
   carry no alignment rule, so the same values now go out and back through a
   host buffer for **0.17 ms**.

## Caveats

- tok/s is noisy at this scale and should not be used to judge changes smaller
  than ~3%.
- Verified at mt=1024 and mt=256, both greedy, b=8, DP4+EP. Other batch sizes
  and sampling modes are unverified.
